# Design systems for humans and AI agents: best practice, October 2026

Researched 2026-10-27 for the Fa Design System (React 19, Tailwind v4, React Aria, Figma-synced, git-tagged npm package, Claude Code skill, Storybook).

Confidence labels used throughout:

- **[V]** verified: I read the primary page (URL given).
- **[VC]** vendor claim: read, but the source sells the thing it describes, or the numbers are self-reported.
- **[U]** unverified: from memory or a search snippet only. Check before relying on it.

---

## 0. Executive summary

1. **Machine interfaces are now table stakes.** In a July 2026 field study of 21 design systems, 18 ship an official MCP server, 18 ship agent skills, and 15 publish llms.txt [V, state-of-ai-in-design-systems.netlify.app/insights]. The debate has moved to how to keep agents on-system, not whether to bother.
2. **Instruction alone is weak; structure and checks are strong.** The study's best systems gate the task (the agent must call a tool or CLI to get component source), give agents exemplars to copy, and run validators in a loop. Atlassian, Meta (Astryx), Shopify, Primer, shadcn and Fluent all do some version of this [V, same source].
3. **The cheapest effective thing is a short rules file naming your own decisions.** Supernova's 36-run test: a 12-line CLAUDE.md took broken team rules from 20 to 0 across 9 runs on a small model, because shadcn's MCP only knows the catalogue, not team decisions [VC: Supernova sells an alternative, n is tiny, one repo, one date: 2026-10-21; supernova.io/blog/shadcn-mcp-design-system]. The finding that agents prefer the library's built-in equivalent over your wrapped one (AlertDialog over ConfirmDestructive) is the useful part.
4. **A single portable "DESIGN.md" is worse than skills/MCP in a real codebase.** Atlassian measured about 92% more tokens, 2.7x variance, and more re-created components with DESIGN.md versus MCP or skill [VC, self-run, Atlassian says "not conclusive"; atlassian.com/blog/.../atlassians-design-md-is-here...]. It is useful for blue-sky prototyping in tools that cannot install your package.
5. **Generated, not hand-written, agent docs.** Mantine, Cloudscape, HeroUI, Atlassian and Astryx compile llms.txt, per-component docs and skill reference files from the same source as the human docs, so nothing drifts [V, field study]. Our per-component markdown in `skills/fa-design-system/references/components/` is hand-maintained; that is our biggest structural risk.
6. **Measure.** Atlassian runs an internal task benchmark and reads transcripts; Meta publishes a nightly ledger (its own system lost 50 of 91 nights to a shadcn baseline, and it publishes that) [V]. Almost nobody else publishes numbers. A small eval set of our own is high value and cheap.
7. **For PM prototyping, the winning pattern is "your real package + guidelines + a template", not a generic app builder.** Figma Make kits (npm package + guidelines folder) and Claude Design (reads your codebase/design files, `/design-sync`) both exist now [V, vendor docs]. Generic builders (Lovable) have weak custom design system support [VC, a competitor's comparison blog].

### 1.2 Marketing vs reality: skeptical notes

- "MCP server" is not one thing. Some servers return content (props tables, source), some return only links or install commands (Untitled UI), some are read-only doc search. Check the tool list: `get_*`/`list_*` are retrieval [V, Supernova, general advice].
- Fluent, Polaris and SLDS show heavy investment on one side and nothing public on the other [V, field study]. Having "an AI story" is not evidence it works.
- Several vendor pages (Supernova, Builder.io, Magic Patterns) are marketing for a competing product. Treat their comparisons as hypotheses.
- Atlassian: its CLI beat its own MCP on speed (8%) and tokens (8%), and agents chose the CLI 60% more [VC, self-run, same benchmark]. The honest takeaway is "MCP, CLI and skill should share one content source", not "CLI wins".
- Storybook MCP is labelled **preview** and the manifest API "may change" [V]. Fine to adopt, not to depend on.
- I found **no independent, peer-reviewed benchmark** of design-system adherence in AI-generated UI. Everything quantitative is vendor-run (Atlassian, Meta, Supernova).

## 4. Evaluating AI output against a design system

### 4.1 What exists (all vendor-run)

- **Atlassian internal benchmark**: a bank of real front-end tasks, auto-graded, same agent and model; records pass rate, time, tokens, tool calls, and **keeps every transcript** because "a benchmark tells you whether the agent succeeded, whereas the transcript tells you whether it succeeded the way you intended" [VC: atlassian.com/blog/ai-at-work/giving-ai-agents-design-system-context-from-the-terminal...]. Results from a login-screen task: no context ~5% design-system context, 4.20M tokens; ADS MCP ~80%, 3.75M; ADS skill ~80%, 4.43M; DESIGN.md ~30%, 7.21M [VC: Atlassian DESIGN.md post, June 2026]. Atlassian itself says not conclusive.
- **Meta Astryx nightly "vibe tests"**: 4 targets (Astryx, Astryx+Tailwind, shadcn/Tailwind baseline, raw HTML), 6 dimensions (Correctness, Accessibility, Code Quality, Efficiency, Maintainability by static analysis; Design by a vision model vs 62 designer-reviewed reference images across 55 prompts). Ledger public on the repo wiki: baseline won 50 of 91 nights, Astryx 19, Astryx+Tailwind 9, 13 ties. Metrics include **decisions per element**, **semantic-token ratio** and **escape hatches** (did the model drop to raw CSS/HTML) [VC but unusually transparent: github.com/facebook/astryx/wiki/Vibe-Evaluation; field study]. The harness's neutrality was not audited by the field study.
- **Astryx API naming by measurement**: the `items` vs `options` prop was settled by running 8 prompts x 3 variants (24 sub-agents), including a no-docs arm to measure the model's prior [V: github.com/facebook/astryx/pull/479].
- **shadcn** keeps `evals.json` for its skill [V, field study].
- **Supernova 18-run, 36-session test** (see summary point 3) is a model for a cheap internal eval: list 5 rules that are yours, pick 3 weekly tasks, run with and without, count where the library's equivalent was used [VC; method is reusable].
- **Anthropic skill-creator**: eval queries (10 should trigger, 10 should not) to tune a skill description [U: Termdock summary of skill-creator; check the skill-creator skill itself].

### 4.2 Checks you can automate for Fa (mostly standard tooling)

| Check                                         | How                                                                                                                                              | Cost        |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------- |
| Palette/hex ban                               | `@shadcn/lint` `no-raw-colors` (Tailwind-aware, suggests nearest theme token) or custom ESLint `no-restricted-syntax` regex on class strings     | Low         |
| Arbitrary values                              | `no-arbitrary-values`                                                                                                                            | Low         |

| Semantic-token ratio                          | Grep class names against `theme.css` token list                                                                                                  | Low         |
| Accessibility                                 | `eslint-plugin-jsx-a11y` + axe via Storybook test-runner / Playwright                                                                            | Medium      |
| Visual regression                             | Storybook + Chromatic or Playwright screenshots of golden pages, light/dark/mobile                                                               | Medium      |

| Transcript review                             | Read agent traces for ignored instructions (Atlassian)                                                                                           | Manual      |

Principle from Meta: AI review is **advisory**, the merge gate is **deterministic** ("no LLM in the enforcement path") [V, field study].

### 4.3 Human review rubric (proposal, not from a source)

Score 0/1 each, pass at 8 of 10: (1) every UI element is a Fa component or documented pattern; (2) zero palette/hex colors; (3) correct brand prop on header/footer; (4) icons from `fa-icons` only; (5) dark mode works with no `dark:` color variants; (6) mobile width intact; (7) copy follows the Norwegian UI wording rules; (8) one primary action per view, destructive actions use the prompt pattern; (9) no invented components (anything new has a Figma frame or is flagged); (10) focus order and labels pass a keyboard run.

## 5. Governance for humans

### 5.1 News/media systems

I could verify little about AI-specific practice at news publishers.

- **Guardian Source** [V]: component library repo (`guardian/source`, Apache-2.0) archived 2022-12-06 and moved to `guardian/csnx`; it shipped its own **ESLint plugins** (`eslint-plugin-source-foundations`, `eslint-plugin-source-react-components`), used **changesets**, and ran an **RFC process** in `docs/rfcs` (e.g. an RFC "disallowing potentially unusable components"). The ESLint-plugin plus RFC combination is the human-governance analogue of what the AI-era systems now automate. Site: theguardian.design.
- **Schibsted** [partly V]: a small team built a design system for multiple news brands (WAN-IFRA, Jan 2019, wan-ifra.org/2019/01/schibsted-builds-design-system-for-multiple-news-brands/); Schibsted's public page mentions a fuller Figma system for designers [snippet only]. Relevant because Finansavisen/Kapital/Motor is the same one-system, many-brands shape (our `brand` prop). I found no Schibsted AI-agent material.
- **BBC GEL, FT Origami, NYT, Bloomberg, Amedia, Aftenposten**: **not verified** in this research. I do not have sources; do not cite them from this report.
- Evidence from the AI field study: none of the 21 systems studied is a news publisher [V]. News-specific AI-design-system practice is an open field.

### 5.2 General governance practices (with source status)

- **Contribution model**: RFCs for new components (Guardian) [V]; Astryx puts a `/create-component` command and wiki-defined lifecycle in the repo so contributors (and agents) follow one protocol [V]. Our CLAUDE.md already encodes "Figma first, then code" and "report gaps, don't decide".
- **Pattern library vs component library**: the field study shows the leaders ship **page and block templates** as first-class, graded artifacts alongside components (Astryx `template`, Untitled UI page templates) [V]. For a newsroom, patterns (article page, teaser grid, market table, paywall) carry more of the identity than atoms. Our `page-patterns.md` is the right start; promote patterns to reviewed code exemplars.
- **Figma-first vs code-first**: both ends are tooled now (Figma MCP writes to canvas; Code Connect maps code to Figma). Astryx is code-first with no Figma binding [V]; Figma-first teams use Code Connect plus guidelines. Our rule (Figma first, parity doc for gaps) stays workable; the missing piece is making parity machine-readable (see 6).
- **Legacy/debt and moving off a bought kit**: I found no authoritative source on migrating away from Untitled UI. Practical advice from the evidence: (a) the library is already forked, so the debt is **stray upstream defaults** (palette classes, `@untitledui/icons`, un-bound Figma components); lint rules (palette ban, restricted imports) find these mechanically; (b) block the upstream MCP in Fa projects (it will re-install upstream components); (c) track remaining upstream-derived components in `docs/figma-parity.md` with a status column. Check the Untitled UI licence terms for redistribution/ejecting with a lawyer, since `files` ships component source in our package [U: licence not read].
- **Deprecation**: Storybook lets you exclude deprecated-component docs/stories from the AI manifest via `!manifest` tag, so agents don't copy them [V: storybook.js.org/docs/ai/best-practices]. Add a `deprecated` marker in the generated component index and in JSDoc (`@deprecated`) that the allow-list reads.
- **Treat agent files as versioned, tested software**: Mantine version-locks its MCP to each release; Atlassian regenerates all entry points from one source; Meta runs nightly [V, field study].

## 6. Recommended architecture for Fa, ranked by impact/effort

Current state (read from repo): SKILL.md (20.9 KB) + 39 component pages + page-patterns + tokens + anti-patterns + layout; `docs/agents/page-analysis.md`; `docs/figma-parity.md`; Storybook with `.storybook/`; no Storybook MCP/manifest, no llms.txt, no lint-for-agents, no evals found by grep.

### Tier 1: do first (high impact, low effort, days)

1. **Lint rules as the enforcement layer** (impact high, effort low).
    - Add `@shadcn/lint` (or equivalent `no-restricted-syntax`/`no-restricted-imports`) in the _consumer_ ESLint preset shipped by the package: `no-raw-colors`, `no-arbitrary-values`, `no-restyle` (with contracts), block `@untitledui/icons`, `lucide-react`, direct `react-aria-components`. Check Tailwind v4 compatibility before adopting [U: I did not verify the package supports v4 theme parsing; its README says "built for Tailwind"].
    - Ship `fa-design-system/eslint` and have `setup.mjs` wire it. The skill then says "run `npm run lint` until clean" (Astryx and Polaris validation-loop pattern).
2. **Generate, don't hand-write, the agent reference** (impact high, effort low-medium).
    - Build script reads component TSX (react-docgen-typescript) + Storybook meta and emits: component allow-list (with sub-components and `deprecated`), props tables, import paths; fail `npm test` if the generated block in `references/components/*.md` or SKILL.md is stale. Keep prose (when-to-use, do/don't) hand-written in the same files, generated tables between markers (Astryx uses `<!-- ASTRYX:START -->` markers) [V].
    - Add a "components that exist" table to SKILL.md (Ant/Carbon pattern).
3. **Anti-pattern pairs and a self-check paragraph** (impact medium, effort very low): rewrite `anti-patterns.md` as "do not X -> use Y" pairs; add the Astryx-style closing instruction to re-read output and replace any raw element, palette color or inline style [VC for the 4x number; mechanism is cheap].
4. **Mini eval set** (impact high, effort low): 8 to 12 briefs drawn from real PM asks (e.g. "Børs list with watchlist", "paywalled Kapital opinion", "Motor test-drive card grid"). For each, a script scores: lint clean, component-purity ratio, token-only colors, brand prop present, no forbidden imports, builds, axe clean. Run with and without skill, and with each model you use; store results in git (`evals/`). Read transcripts for the first runs (Atlassian lesson). This is also how to settle naming/API questions (Astryx PR 479 method).

### Tier 2: next (high impact, medium effort, 1 to 3 weeks)

5. **Golden pages**: 4 to 6 full reference pages (front page, article, market table page, forum thread, form/settings, MittFA feed) built from real components, in the package under `examples/` and as Storybook "Pages". Grade them with the component-purity script; point the skill to them as "copy this". Evidence: Astryx exemplar strategy [VC].
6. **Storybook MCP + components manifest** (impact medium, effort low-medium): enable `features.componentsManifest`, add `@storybook/addon-mcp`, add JSDoc summaries and prop descriptions, make each story one concept with a "why" description, tag anti-pattern stories `!manifest` [V, Storybook best-practices]. Preview status: do not make it the only channel. Our stories are demos-oriented (`*.demo.tsx` imported by stories), so check that the manifest picks up snippets.
7. **Prototype starter repo** `fa-prototype-starter` (impact high for PMs, effort medium): Vite + the package + AGENTS.md block + golden pages + lint + preview deploy (Vercel/Netlify) + a README with 5 example prompts. Brief PMs to decompose features into small steps (Builder.io advice, VC but sensible).
8. **Machine-readable parity** (impact medium, effort low-medium): convert `docs/figma-parity.md` into a table that is also emitted as `parity.json` and referenced by the skill ("component X is partial in Figma; ask before extending") so agents obey the CLAUDE.md "report gaps" rule without reading a long doc.

### Tier 3: later or optional

9. **CLI/MCP of your own** (`npx fa-design-system component Button --json`, `search`, `tokens`) on top of the generated data, following Atlassian (one content model, many entry points) and Astryx. Worth it once Tier 1 generation exists; effort medium. Skip a hosted MCP until there are non-Claude-Code consumers.
10. **Figma Make kit / Claude Design import** for PMs who avoid Claude Code. Requires publishing to npm or Figma's private registry; write `guidelines/` from the skill (nearly a copy). Pilot with 2 PMs before investing. Claude Design's standalone version retires 2026-12-14; use the in-Claude version.
11. **Code Connect** for the ~15 most used components with per-mapping custom instructions (effort medium, benefit limited to Figma-originated work). Leaders mostly do not do it [V].
12. **Visual regression on golden pages** (Chromatic or Playwright), plus vision-judge scoring as advisory only.
13. **DTCG export** of tokens, `llms.txt`, `DESIGN.md` export for external tools: all cheap but only help non-Claude-Code consumers. Do last.

### Things not to do

- Do not rely on a single big DESIGN.md or CLAUDE.md as the system [VC: Atlassian; also Supernova's own caveats on per-repo drift].
- Do not attach the Untitled UI MCP to Fa projects.
- Do not add new components to code without a Figma frame (existing rule) even when an agent proposes one; make the lint/eval flag "invented component" so humans see it.
- Do not trust vendor benchmark numbers; reproduce on your own briefs.

### Measures of success

Lint-clean rate on first generation, component-purity ratio, count of invented components per prototype, tokens/time per task, and PM-reported "needed engineer rework" per prototype. Track per skill version (tag the skill release like the package).
